SOLID Principles — Java

Five principles for writing maintainable, extensible object-oriented code

S - Single Responsibility O - Open/Closed L - Liskov Substitution I - Interface Segregation D - Dependency Inversion ← Index
S

Single Responsibility Principle

A class should have only one reason to change. One class = one job.

// BAD: UserService does everything
public class UserService {
    private Connection db;

    public void createUser(User user) {
        // 1. Validates user
        if (user.getEmail() == null) throw ...;

        // 2. Saves to DB
        db.execute("INSERT INTO users ...");

        // 3. Sends email
        SmtpClient smtp = new SmtpClient();
        smtp.send(user.getEmail(), "Welcome!");

        // 4. Logs action
        Logger.info("User created: " + user.getId());
    }
}
// Problems: 4 reasons to change!
// GOOD: Each class has one responsibility
public class UserValidator {
    public void validate(User user) {
        if (user.getEmail() == null)
            throw new InvalidUserException();
    }
}
public class UserRepository {
    public void save(User user) { /* DB logic */ }
}
public class EmailService {
    public void sendWelcome(User user) { /* email */ }
}
public class UserService {
    public void createUser(User user) {
        validator.validate(user);
        repository.save(user);
        emailService.sendWelcome(user);
    }
}

Benefits

  • Easier to test each component in isolation
  • Changes to email logic don't affect DB logic
  • Classes are smaller and more readable
  • Better code reuse across the application
O

Open/Closed Principle

Software entities should be open for extension, but closed for modification.

// BAD: Adding new discount requires modifying class
public class DiscountCalculator {
    public double calculate(Order order, String type) {
        if (type.equals("STUDENT")) {
            return order.getTotal() * 0.1;
        } else if (type.equals("EMPLOYEE")) {
            return order.getTotal() * 0.2;
        } else if (type.equals("SENIOR")) {
            return order.getTotal() * 0.15;
        }
        // Adding VIP requires changing this class!
        return 0;
    }
}
// GOOD: New discounts via extension, not modification
public interface DiscountStrategy {
    double calculate(Order order);
}
public class StudentDiscount implements DiscountStrategy {
    public double calculate(Order o) { return o.getTotal() * 0.1; }
}
public class EmployeeDiscount implements DiscountStrategy {
    public double calculate(Order o) { return o.getTotal() * 0.2; }
}
// Adding VIP: just add a new class, no existing code changes!
public class VipDiscount implements DiscountStrategy {
    public double calculate(Order o) { return o.getTotal() * 0.3; }
}
public class DiscountCalculator {
    public double calculate(Order o, DiscountStrategy strategy) {
        return strategy.calculate(o);
    }
}

Key Techniques

  • Strategy pattern: inject behavior via interfaces
  • Template method: define algorithm skeleton, let subclasses fill in steps
  • Decorator pattern: add behavior by wrapping objects
  • Plugin architecture: discover implementations at runtime
L

Liskov Substitution Principle

Subtypes must be substitutable for their base types without altering program correctness.

// BAD: Square violates LSP for Rectangle
public class Rectangle {
    protected int width, height;
    public void setWidth(int w) { width = w; }
    public void setHeight(int h) { height = h; }
    public int area() { return width * height; }
}
public class Square extends Rectangle {
    @Override
    public void setWidth(int w) {
        width = height = w; // VIOLATES: changes height too!
    }
    @Override
    public void setHeight(int h) {
        width = height = h; // VIOLATES: changes width too!
    }
}
// This breaks with Square:
Rectangle r = new Square();
r.setWidth(5);
r.setHeight(3);
// Expected: 15, Actual: 9 (Square forced both to 3)
// GOOD: Don't force Square into Rectangle hierarchy
public interface Shape {
    int area();
}
public class Rectangle implements Shape {
    private final int width, height;
    public Rectangle(int w, int h) { width=w; height=h; }
    public int area() { return width * height; }
    // Immutable - no setters breaking assumptions
}
public class Square implements Shape {
    private final int side;
    public Square(int side) { this.side = side; }
    public int area() { return side * side; }
}
// Now they're peers, not parent/child
// No LSP violation - they share the Shape interface

LSP Rules for Subclasses

  • Preconditions cannot be strengthened (accept at least what parent accepts)
  • Postconditions cannot be weakened (guarantee at least what parent guarantees)
  • Invariants of the parent must be preserved
  • Methods that throw exceptions must only throw parent exception types
I

Interface Segregation Principle

Clients should not be forced to depend on interfaces they don't use.

// BAD: Fat interface forces unused method stubs
public interface Worker {
    void work();
    void eat();
    void sleep();
}
// Robot can't eat or sleep!
public class Robot implements Worker {
    public void work() { /* real work */ }
    public void eat() { throw new UnsupportedOperationException(); }
    public void sleep() { throw new UnsupportedOperationException(); }
    // Forces robots to know about "eating" - a human concern
}
// GOOD: Small, focused interfaces
public interface Workable { void work(); }
public interface Feedable  { void eat(); }
public interface Sleepable { void sleep(); }

// Human needs all three
public class Human implements Workable, Feedable, Sleepable {
    public void work()  { /* work */ }
    public void eat()   { /* eat */ }
    public void sleep() { /* sleep */ }
}

// Robot only needs Workable
public class Robot implements Workable {
    public void work() { /* work */ }
    // No stubs needed!
}

// You can also compose them
public interface HumanWorker extends Workable, Feedable, Sleepable {}

Benefits

  • Smaller interfaces are easier to implement and mock in tests
  • Reduces coupling — classes only depend on what they need
  • Avoids "throw UnsupportedOperationException" anti-pattern
  • Enables more granular dependency injection
D

Dependency Inversion Principle

High-level modules should not depend on low-level modules. Both should depend on abstractions.

// BAD: High-level depends on low-level concrete class
public class OrderService {
    // Directly depends on concrete MySQL implementation!
    private MySqlOrderRepository repository
        = new MySqlOrderRepository();

    public void placeOrder(Order order) {
        repository.save(order);
        // Can't switch to Postgres without changing this class
        // Can't mock in tests without real DB connection!
    }
}
// GOOD: Both depend on the abstraction
public interface OrderRepository {
    void save(Order order);
    Optional<Order> findById(long id);
}
// Low-level: implements the abstraction
public class MySqlOrderRepository implements OrderRepository {
    public void save(Order o) { /* MySQL */ }
    public Optional<Order> findById(long id) { /* MySQL */ }
}
// High-level: depends on the abstraction
public class OrderService {
    private final OrderRepository repository;

    // Dependency is injected (constructor injection)
    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }
    public void placeOrder(Order order) {
        repository.save(order);
        // Now you can inject: MySql, Postgres, InMemory, Mock!
    }
}

Injection Styles

  • Constructor injection (preferred): dependencies required at creation, easy to test
  • Setter injection: optional dependencies, allows reconfiguration
  • Field injection (@Autowired): convenient but harder to test without container
  • Method injection: for methods that need a dependency only for that call
