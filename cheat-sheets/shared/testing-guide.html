The Testing Pyramid

End-to-End Tests

Fewest (5-10%) — Slow, expensive, brittle

Integration Tests

Some (20-30%) — Test component interaction

Unit Tests

Most (60-70%) — Fast, isolated, reliable

End-to-End Tests

Test complete user workflows through the entire application stack (UI → API → DB).

  • ✓
    Best forCritical user journeys: login, checkout, signup
  • ✗
    Avoid forEvery feature — too slow and flaky
Tools

Java: Selenium, Playwright, Cypress, TestContainers

Python: Selenium, Playwright, pytest + requests, Behave (BDD)

Key metrics: ~minutes per test, run in CI nightly or pre-release

Integration Tests

Test interactions between components: service + repository, controller + service, multiple modules together.

  • ✓
    Use real dependenciesReal DB (in-memory or TestContainers), real HTTP clients
  • ✓
    Test contractsVerify JSON serialization, DB schema, API contracts
  • ✗
    Don't test all pathsUnit tests cover edge cases; integration tests cover happy paths
Tools

Java: Spring Boot Test (@SpringBootTest), TestContainers, H2 in-memory DB, RestAssured, WireMock

Python: pytest + TestContainers, SQLAlchemy + SQLite, httpx TestClient, responses (mock HTTP)

Unit Tests

Test individual units in complete isolation. No DB, no network, no filesystem — mock all external dependencies.

  • ✓
    FastShould run in milliseconds; full suite in seconds
  • ✓
    IsolatedOne test failing shouldn't affect others
  • ✓
    DeterministicSame input always gives same result
  • ✓
    Self-documentingTest name explains what behavior is tested
  • ✗
    Don't test implementationTest behavior (what), not implementation (how)
Tools

Java: JUnit 5, Mockito, AssertJ, Hamcrest

Python: pytest, unittest, unittest.mock, pytest-mock

Other Test Types

Property-Based Testing

Generate random inputs to find edge cases automatically.

# Python: hypothesis
from hypothesis import given, strategies as st

@given(st.lists(st.integers()))
def test_sort_preserves_length(lst):
    assert len(sorted(lst)) == len(lst)

@given(st.text())
def test_encode_decode_roundtrip(s):
    assert s.encode().decode() == s
Java: jqwik library provides similar property-based testing
Contract Testing

Verify that API providers and consumers agree on interface contracts.

Tools: Pact (Java/Python), Spring Cloud Contract

  • Consumer defines expected request/response contracts
  • Provider verifies it honors the contracts
  • Catches breaking API changes before deployment
Mutation Testing

Verify test quality by introducing bugs (mutations) and checking that tests catch them.

Java: PIT (pitest) — industry standard
Python: mutmut, cosmic-ray

Mutation score > 80% indicates high-quality test suite

Test-Driven Development (TDD)

1. Red 🔴

Write a failing test first. The test describes the behavior you want to implement. It MUST fail.

→

2. Green 🟢

Write the minimum code to make the test pass. Don't over-engineer — just make it green.

→

3. Refactor 🔵

Improve the code while keeping tests green. Remove duplication, improve names, extract methods.

→

Repeat

Write the next failing test for the next piece of behavior. Keep cycles small (minutes).

TDD Example: FizzBuzz

Step 1: Red — Write failing test first
@Test
void returns_1_for_number_1() {
    FizzBuzz fb = new FizzBuzz();
    assertEquals("1", fb.convert(1));
}
// FizzBuzz class doesn't exist yet → COMPILE ERROR (Red)
def test_returns_1_for_number_1():
    assert fizzbuzz(1) == "1"
# Function doesn't exist → NameError (Red)
Step 2: Green — Minimum code to pass
public class FizzBuzz {
    public String convert(int n) {
        return "1";  // Hardcoded! But test passes
    }
}
def fizzbuzz(n):
    return "1"  # Hardcoded! But test passes
More tests drive better design
// Each new test forces better implementation
@Test void returns_2_for_2() { assertEquals("2", fb.convert(2)); }
@Test void returns_Fizz_for_3() { assertEquals("Fizz", fb.convert(3)); }
@Test void returns_Buzz_for_5() { assertEquals("Buzz", fb.convert(5)); }
@Test void returns_FizzBuzz_for_15() { assertEquals("FizzBuzz", fb.convert(15)); }

// Final implementation (after refactoring)
public String convert(int n) {
    if (n % 15 == 0) return "FizzBuzz";
    if (n % 3 == 0)  return "Fizz";
    if (n % 5 == 0)  return "Buzz";
    return String.valueOf(n);
}
def test_returns_2_for_2():  assert fizzbuzz(2) == "2"
def test_returns_fizz_for_3(): assert fizzbuzz(3) == "Fizz"
def test_returns_buzz_for_5(): assert fizzbuzz(5) == "Buzz"
def test_returns_fizzbuzz_for_15(): assert fizzbuzz(15) == "FizzBuzz"

# Final implementation
def fizzbuzz(n: int) -> str:
    if n % 15 == 0: return "FizzBuzz"
    if n % 3 == 0:  return "Fizz"
    if n % 5 == 0:  return "Buzz"
    return str(n)
TDD Benefits & Misconceptions
  • ✓
    Forces good designHard-to-test code = poorly designed code
  • ✓
    DocumentationTests show how to use the code
  • ✓
    ConfidenceRefactor freely — tests catch regressions
  • ✗
    Not about 100% coverageTDD is a design tool, not a coverage metric
  • ✗
    Not slowerDebugging time saved > test writing time

Unit Testing in Java (JUnit 5)

JUnit 5 Essentials
import org.junit.jupiter.api.*;
import static org.assertj.core.api.Assertions.*;

class CalculatorTest {

    @Test
    @DisplayName("should add two positive numbers correctly")
    void add_twoPositiveNumbers_returnsSum() {
        // Arrange
        Calculator calc = new Calculator();
        // Act
        int result = calc.add(2, 3);
        // Assert
        assertThat(result).isEqualTo(5);
    }

    @ParameterizedTest
    @CsvSource({"1,2,3", "0,0,0", "-1,1,0", "100,200,300"})
    void add_parameterized(int a, int b, int expected) {
        assertThat(new Calculator().add(a, b)).isEqualTo(expected);
    }

    @Test
    void divide_byZero_throwsException() {
        Calculator calc = new Calculator();
        assertThatThrownBy(() -> calc.divide(10, 0))
            .isInstanceOf(ArithmeticException.class)
            .hasMessageContaining("zero");
    }

    @BeforeEach void setUp() { /* runs before each test */ }
    @AfterEach  void tearDown() { /* runs after each test */ }
    @BeforeAll  static void setUpClass() { /* once before all */ }
    @AfterAll   static void tearDownClass() { /* once after all */ }

    @Disabled("Skipped until bug #123 is fixed")
    @Test void skippedTest() { }

    @Nested
    class WhenDividing {
        @Test void exactDivision() { /* nested test */ }
    }
}
AssertJ — Fluent Assertions
// Primitives and objects
assertThat(result).isEqualTo(42);
assertThat(name).isEqualTo("Alice").isNotNull();
assertThat(value).isGreaterThan(0).isLessThan(100);
assertThat(text).startsWith("Hello").endsWith("!");
assertThat(text).contains("World").doesNotContain("Foo");

// Collections
assertThat(list).hasSize(3)
                .containsExactly(1, 2, 3)
                .doesNotContain(4);
assertThat(list).extracting("name")
                .containsExactlyInAnyOrder("Alice", "Bob");

// Maps
assertThat(map).containsKey("name")
               .containsEntry("age", 30);

// Exceptions
assertThatThrownBy(() -> sut.doSomething())
    .isInstanceOf(IllegalArgumentException.class)
    .hasMessage("Invalid input");

// Soft assertions (don't stop on first failure)
SoftAssertions softly = new SoftAssertions();
softly.assertThat(result.getName()).isEqualTo("Alice");
softly.assertThat(result.getAge()).isEqualTo(30);
softly.assertAll();

Unit Testing in Python (pytest)

pytest Essentials
import pytest

# Simple test
def test_add_two_positive_numbers():
    result = Calculator().add(2, 3)
    assert result == 5

# Parametrized tests
@pytest.mark.parametrize("a,b,expected", [
    (1, 2, 3),
    (0, 0, 0),
    (-1, 1, 0),
    (100, 200, 300),
])
def test_add_parametrized(a, b, expected):
    assert Calculator().add(a, b) == expected

# Exception testing
def test_divide_by_zero():
    with pytest.raises(ZeroDivisionError, match="division by zero"):
        Calculator().divide(10, 0)

# Fixtures (dependency injection for tests)
@pytest.fixture
def calculator():
    return Calculator()

@pytest.fixture
def db_session():
    session = create_test_session()
    yield session  # test runs here
    session.rollback()  # cleanup

def test_with_fixture(calculator):
    assert calculator.add(1, 2) == 3

# Marks
@pytest.mark.skip(reason="Bug #123 not fixed")
def test_skipped(): pass

@pytest.mark.slow
def test_performance(): pass  # run with: pytest -m slow

Mockito (Java)
import static org.mockito.Mockito.*;
import static org.mockito.ArgumentMatchers.*;

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock private OrderRepository repository;
    @Mock private EmailService emailService;
    @InjectMocks private OrderService orderService;

    @Test
    void placeOrder_validOrder_savesAndNotifies() {
        // Arrange: stub repository
        Order order = new Order("item1", 100.0);
        when(repository.save(order)).thenReturn(42L);

        // Act
        long orderId = orderService.place(order);

        // Assert: verify interactions
        assertThat(orderId).isEqualTo(42L);
        verify(repository).save(order);
        verify(emailService).sendConfirmation(42L, order.getEmail());
        verifyNoMoreInteractions(emailService);
    }

    @Test
    void getOrder_notFound_throwsException() {
        when(repository.findById(anyLong()))
            .thenReturn(Optional.empty());

        assertThatThrownBy(() -> orderService.getOrder(99L))
            .isInstanceOf(OrderNotFoundException.class);
    }

    // Argument captors
    @Captor ArgumentCaptor<Order> orderCaptor;

    @Test
    void verifyExactArgument() {
        orderService.place(new Order("item", 50.0));
        verify(repository).save(orderCaptor.capture());
        assertThat(orderCaptor.getValue().getTotal()).isEqualTo(50.0);
    }
}
unittest.mock (Python)
from unittest.mock import Mock, MagicMock, patch, call
import pytest

class TestOrderService:
    @pytest.fixture
    def repository(self):
        return Mock()

    @pytest.fixture
    def service(self, repository):
        return OrderService(repository=repository)

    def test_place_order_saves_to_repository(self, service, repository):
        order = Order("item1", 100.0)
        repository.save.return_value = 42

        order_id = service.place(order)

        assert order_id == 42
        repository.save.assert_called_once_with(order)

    def test_place_order_raises_on_db_error(self, service, repository):
        repository.save.side_effect = DatabaseError("Connection failed")
        with pytest.raises(OrderError):
            service.place(Order("item", 10.0))

    # patch: replace at the import location
    @patch("myapp.services.send_email")
    def test_place_order_sends_email(self, mock_send, service):
        service.place(Order("item", 10.0))
        mock_send.assert_called_once()
        args = mock_send.call_args
        assert "order_id" in args.kwargs

    # Context manager style
    def test_with_patch(self, service):
        with patch("myapp.services.datetime") as mock_dt:
            mock_dt.now.return_value = datetime(2024, 1, 1)
            result = service.get_timestamp()
            assert result == datetime(2024, 1, 1)
pytest-mock (Pythonic Style)
import pytest

def test_order_service(mocker):
    # mocker fixture from pytest-mock
    mock_repo = mocker.Mock()
    mock_repo.save.return_value = 42

    # patch at module level
    mocker.patch("myapp.send_email")

    service = OrderService(repository=mock_repo)
    order_id = service.place(Order("item", 50.0))

    assert order_id == 42
    mock_repo.save.assert_called_once()

# Spy: wrap real object, still calls real methods
def test_with_spy(mocker):
    calculator = Calculator()
    spy = mocker.spy(calculator, "add")

    result = calculator.add(2, 3)

    assert result == 5                    # real method called
    spy.assert_called_once_with(2, 3)    # verified

# Auto-spec: Mock that validates method signatures
mock_repo = mocker.create_autospec(OrderRepository)
# Now mock_repo.save() raises TypeError if called with wrong args!

Testing Best Practices

FIRST Principles
  • F
    FastTests should run in milliseconds, not seconds. Full suite < 1 minute.
  • I
    IndependentTests don't depend on each other. Any order, any subset should work.
  • R
    RepeatableSame result on any machine, any time, any environment.
  • S
    Self-ValidatingTests either pass or fail — no manual inspection needed.
  • T
    TimelyWrite tests before (TDD) or alongside the code, not months later.
AAA Pattern — Arrange, Act, Assert
@Test
void should_apply_discount_for_vip_customer() {
    // ARRANGE: set up the state
    Customer vip = new Customer("Alice", CustomerTier.VIP);
    Order order = new Order(vip, List.of(new Item("phone", 1000.0)));
    DiscountService service = new DiscountService();

    // ACT: execute the behavior being tested (ONE line ideally)
    double discountedTotal = service.applyDiscount(order);

    // ASSERT: verify the outcome
    assertThat(discountedTotal).isEqualTo(900.0); // 10% VIP discount
}
When assertions get complex, consider extracting a helper method
Naming Conventions

Good test names act as living documentation:

// Pattern: methodName_scenario_expectedBehavior
void add_twoPositives_returnsSum() {}
void divide_byZero_throwsArithmetic() {}
void placeOrder_insufficientStock_returnsError() {}
void findUser_nonExistentId_returnsEmpty() {}

// Or Given/When/Then style (BDD)
void givenVipCustomer_whenApplyingDiscount_thenReceives10Percent() {}
# Python: descriptive, snake_case
def test_add_returns_sum_of_two_positives(): ...
def test_divide_raises_zero_division_error(): ...
def test_place_order_with_insufficient_stock(): ...

# Class grouping (often clearer)
class TestUserService:
    class WhenUserExists:
        def test_returns_user_data(self): ...
        def test_updates_last_seen(self): ...
    class WhenUserNotFound:
        def test_raises_not_found_error(self): ...
What NOT to Test
  • ✗
    Don't test trivial getters/settersUnless they have logic, testing x.getName() == name wastes time
  • ✗
    Don't test framework codeDon't test that Spring @Autowired works or that JPA saves
  • ✗
    Don't test private methods directlyTest through the public API; if private method is complex, extract a class
  • ✗
    Don't test implementations, test behaviorTests should survive refactoring without changing
  • ✗
    Don't over-mockToo many mocks = testing mock config, not real behavior
Test Coverage — What It Means

Coverage tells you what code was executed, not what was verified.

  • ✓
    Use as a floor, not a target80% coverage should be minimum, not the goal
  • ✓
    Branch coverage > line coverageTests all if/else paths, not just lines executed
  • ✗
    100% coverage ≠ good testsassert(true) covers code without testing anything
Java: JaCoCo. Python: pytest-cov / coverage.py
Test Code Quality
  • ✓
    One assertion per test (ideally)Makes failure messages clear; easier to diagnose
  • ✓
    Use builder pattern or factories for test dataObjectMother/TestDataBuilder pattern reduces duplication
  • ✓
    Keep tests DRY — but not too DRYSome duplication in tests is OK; clarity > deduplication
  • ✗
    Don't add logic to testsif/for/while in tests = tests that need their own tests
  • ✗
    Don't use random data without seedsUse fixed values or property-based testing libraries
